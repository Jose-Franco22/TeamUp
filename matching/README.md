# Matching engine — two-stage team recommender

First iteration. Given a project with open roles, it recommends whole **teams**
of students, not one student at a time.

```
evidence            jury                      judge
--------            ----                      -----
skills + resume  -> point system, beam   ->   LLM reviews the short list
evidence            search over teams          and picks a winner
```

The jury always runs and always produces an answer. The judge only reorders
what the jury found, so the engine still works with no API key, no network, and
no model.

## Running it

```bash
cd matching
node src/demo.mjs                        # every open project, jury only
node src/demo.mjs --project p-parking    # one project
node src/demo.mjs --judge                # also ask the LLM to review
node src/demo.mjs --no-cohort            # only the students in mockData
node --test                              # 19 tests
```

For the judge, copy `.env.example` to `.env` and add a Gemini key. Both `.env`
and `out/` are gitignored: recommendations are about people, so runs stay local.

## Stage 1 — the jury

Every number a student sees can be traced back to these four parts, each scored
0–1 and combined with the weights in `src/scoring.mjs`:

| Part | Weight | What it measures |
| --- | --- | --- |
| coverage | 0.50 | how much of the open roles the team actually fills |
| depth | 0.20 | how well evidenced those skills are |
| breadth | 0.15 | distinct roles covered, so not three of the same |
| hours | 0.15 | whether the team can work at a similar pace |

Supporting rules:

- **Confidence in a skill** starts at 0.5 for a bare tag and rises with months
  of use and shipped projects. A skill confirmed from a resume counts slightly
  higher than one typed in by hand.
- **A neighbouring skill is worth 35%** of the real one. Someone with Figma can
  probably help with React, but it is not the same claim.
- **The search is a beam search** (`src/shortlist.mjs`). Checking every team of
  3 from 24 students means 2,024 combinations, and it gets worse fast, so teams
  are built one member at a time keeping the best 12 partial teams at each step.
- **Ties break on team id,** so the same data always produces the same order.

## Stage 2 — the judge

`src/judge.mjs` sends the short list to Gemini in one call per project, never
one per student, so the free tier's 15 requests a minute is never the limit.

- **Anonymized.** The model sees "Student A, React (14 months, 2 projects), 12
  hrs/wk" — never names, emails or ids. A test asserts this.
- **Bounded.** Team ids are an enum in the response schema, so the judge can
  reorder the short list but cannot invent a team or add a student. Anything
  unknown in the reply is dropped, and forgotten teams keep their jury order.
- **Optional.** No key, a 429, a network error or unparseable JSON all fall back
  to the jury's order, with the reason recorded in the verdict.

In a real run on `p-parking`, the judge preferred a candidate with OpenCV
experience because the project processes camera feeds — a link the point system
cannot see, since it only compares skill ids. It also warned that one student
appeared on all five shortlisted teams.

## Data

Real data comes from `frontend/src/api/mockData.js`, the same shapes as the
Supabase tables, so switching to live queries only touches `src/data.mjs`.

Two things the schema cannot store yet are **temporary test fixtures**,
generated by `node scripts/make-fixtures.mjs` (seeded, so they never drift):

- `fixtures/test-evidence.json` — months of use and project counts per skill.
  Real evidence needs a `profile_evidence` table fed by resume parsing.
- `fixtures/test-cohort.json` — 24 synthetic unteamed students. Only 2 of the 10
  students in `mockData` are unteamed, too few to search over.

## Known limits

- **Open roles are assumed.** `project_roles_needed` is treated as still open,
  because `team_members.role` is free text and cannot be matched back to a
  `skill_id`. Normalizing that column is a prerequisite for exact coverage.
- **The short list repeats people.** All five teams often share the strongest
  candidate. A diversity pass is the obvious next step.
- **Assignment is greedy,** not optimal. Swapping in the Hungarian algorithm
  changes only `assignToSlots`.
- **No interests.** Nothing in the schema stores them, so the jury matches on
  skills, evidence and hours. The judge partly covers this by reading the
  project description.
- **The weights are a first guess.** They need an evaluation harness over
  generated cohorts before anyone defends them in the write-up.

## Next

1. Normalize `team_members.role` to a `skill_id` so coverage is exact.
2. Add the diversity pass, so the short list offers real alternatives.
3. Build the evaluation harness: generated cohorts, then measure roles filled,
   students placed, and how often the judge overrules the jury.
4. Port the jury to a Postgres function so the app can call it through
   `supabase.rpc`, with the judge in an Edge Function.
